# Scheduling from Acceptance Criteria

## My view

I schedule work by defining success before I define activity. For any goal, I start with acceptance criteria: what must be true for the outcome to be complete and successful? That prevents a calendar from becoming a list of busywork.

Once the acceptance criteria are clear, I work backward from the goal. I identify the prerequisites, milestones, reviews, validation, and recovery time required to reach the outcome. I then block time for that work in the order the dependencies require, rather than filling my schedule with the most visible or urgent-looking tasks.

## Competing priorities

When priorities compete, I use the project’s core values as the decision rule. On my current project, those values are security and stability. All else equal, I choose the feature or task that produces the more secure and stable outcome.

The exception is a dependency-chain conflict: the safest or most stable next step may be blocked by a prerequisite. In that case, I make the conflict explicit and schedule the work that unblocks the dependency. The values still guide the destination; dependency chaining determines the viable sequence.

## Skim notes

- Define acceptance criteria before scheduling work.
- Work backward from the successful outcome.
- Identify dependencies, milestones, validation, reviews, and recovery time.
- Block time in dependency order, not by apparent urgency.
- Use project values as the tie-breaker for competing priorities.
- Current project values: security and stability.
- Choose the more secure and stable option unless dependency chaining makes it infeasible now.
- Surface the dependency conflict and schedule the prerequisite work first.

## Interview answer

> I start scheduling by defining the acceptance criteria for the goal—what must be true for the work to be successful. Then I work backward to identify the dependencies, milestones, validation, and time blocks needed to get there. When priorities compete, I use the project’s core values as the decision rule. On my current project, security and stability come first, so I default to the more secure and stable option. The exception is when a dependency-chain conflict blocks that option. In that case, I make the conflict explicit and schedule the prerequisite work needed to unblock it, rather than pretending that the preferred outcome is immediately achievable. That keeps the calendar connected to the real path to a successful outcome.
